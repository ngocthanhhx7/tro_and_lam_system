# Security remediation - 2026-10-23

Baseline: a17fba3. The supplied audit reported zero confirmed findings and 13 leads requiring validation. This work distinguishes reproduced local defects, preventive hardening, and deployment-dependent conditions. All reproduction data is synthetic and local. No real payment, customer order, mail delivery or provider load test was performed.

## Disposition of all 13 leads

| Audit fingerprint | Evidence and action |
| --- | --- |
| account-geocoding.process-budget-monopolization | Photon is enabled on the VPS. The shared one-request-per-second gate protects a public upstream and can still reject concurrent legitimate misses. Added an authenticated per-customer one-request-per-minute allowance before reaching the provider; another customer's allowance remains independent. Manual address entry stays usable. This reduces monopolization by one account, without claiming an availability guarantee for the public provider. |
| api.private-json.responses-without-no-store | Added API-wide `private, no-store`, including failures; immutable media is separate. Client JSON and CSRF fetches explicitly bypass browser caches. A bounded rotating-key test verifies saturation and expiry recovery. This is a process memory bound, not a cluster quota or monetary limit. |
| client.cart-state.stale-after-cross-tab-logout | Real local multi-tab browser regression verifies that logout/account replacement removes the old cart and resolves the new account's own empty cart. Non-sensitive storage nonces signal session changes; private subtrees unmount, cart single-flight state is invalidated, and stale component responses cannot repopulate them. Failed cart reads clear retained cart data. |

Additional hardening: media storage errors use a stable public message; backend PayOS URLs reject alternate ports, matching the browser origin restriction. Provider recovery verifies stored order code, link identity and amount before restoring a URL. Official API reference: https://payos.vn/docs/api/ (GET payment requests accepts a store order code or payment-link ID). No production provider credentials were used for tests.

## Deployment boundaries

The active target before this release was /opt/tro-lam/releases/c6ce592-cart-tune-20261022. Root owns the release parent directories; the trolam runtime cannot edit server source or switch current. The authorized ec2-user operator uploads with the owner's existing key and promotes through sudo. No key/environment secret is placed in an artifact, Git, logs or this report.

Deployment binds a committed revision to archive digests and a frontend build, retains the previous release, prepares indexes without deleting data, checks configuration, switches current atomically, restarts the API and checks readiness. Rollback retains data/indexes and restores the previous application release. The deployment includes the earlier selective Nam integration and approved owner storefront work.

Vercel settings were not inspected: this task deploys the active same-origin VPS frontend/API. Mutable upstream GitHub Action tags remain an optional supply-chain hardening item; the audit did not prove a compromised action or release. Public geocoder fairness and business validation of future regional shipping rates remain the limits described above.

## Verification

Focused local browser regressions passed for cross-tab account/cart replacement, guest proof/order/thread replacement, existing guest verification, and the complete voucher/profile/email/password flow. Focused service tests cover trusted actor binding, private cache headers, bounded limiter state, cooldown index prerequisites, payment creation ownership and duplicate settlement suppression. The full check and browser results are recorded with the release and GitHub Actions.

Normal backend data paths add no new database reads for the cache/actor/limiter fixes. Creation ownership is stored with the existing attempt write; legacy recovery has a versioned claim. A production startup adds one index catalog check. Browser session/proof transitions and focus checks deliberately revalidate identity and reread private views rather than caching authorization, prices, stock or payment state. No VPS performance improvement is claimed from local timings.
